# Link 설계와 저장 경계

[README](../README.md) · [설치](setup.md) · [API](plugin-api.md) · [검증](validation.md)

현재 구현의 동작을 설명하는 문서입니다. 운영 적합성은 [검증 결과](validation.md)에 기록합니다. 아래 영속성 처리는 `journal` 모드에 해당합니다.

## 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| `aspaper-server`의 NMS 패치와 `io.linkmc.server` | 프레임 경계, 플레이어 저장 대체, 입장 처리, 이전 빌드 월드의 일회성 바닐라 내보내기 |
| `link-core` | SQL 최신 상태·outbox, 소유권, 입장권, 정원 예약 |
| `link-api` | 백엔드·프록시 플러그인의 비동기 계약 |
| `link-velocity` | 첫 입장 배정, 준비된 이동 요청의 백엔드 연결 전달 (명령어 없음) |
| `link-integration` | 폐기 가능한 테스트 서버용 플러그인과 프로토콜 클라이언트 |

PostgreSQL 또는 MariaDB가 플레이어 상태와 소유권의 기준입니다. 월드는 바닐라 파일(`level.dat`, region, SavedData)이며 Paper가 로드·저장합니다. Redis는 알림을 전달하며 인벤토리 원본이나 분산 잠금의 기준으로 사용하지 않습니다.

## 비동기 자동 저장

1. 일반 게임 작업과 패킷은 메모리에서 진행합니다. 매 틱마다 전체 저장을 수행하거나 게임 패킷을 DB 뒤에 보류하지 않습니다.
2. 기본 30초 주기, 명시적 저장, 로그아웃 또는 내구성 완료가 필요한 API 요청에서 서버 스레드가 플레이어 상태 복사본을 캡처합니다.
3. Link-Save-Worker 스레드가 복사본의 직렬화를 처리합니다. 실제 Bukkit/NMS 객체는 읽거나 변경하지 않습니다.
4. Link-Save-Commit 스레드가 소유권·예상 버전을 검사하고 최신 상태·중복 요청 영수증·outbox를 원자적으로 커밋합니다. 동시에 처리하는 체크포인트는 하나이며 다음 저장을 무한 큐에 쌓지 않습니다.
5. 서버 스레드가 완료를 확인하고 API 콜백·로그아웃 정리를 수행합니다. 서버 이동과 정상 종료는 최종 저장을 기다리는 경계입니다.

월드는 바닐라 자동 저장으로 region 파일에 저장되며 `/save-all`은 월드 저장 후 플레이어 데이터를 커밋합니다. 저장 실패·지연 한도 초과 시 서버를 중단하며, DB 커밋 응답이 불확실하면 동일 작업을 재시도합니다. Java 객체를 메모리에서 원복하지 않습니다. 일반 게임의 마지막 저장 이후 변경은 강제 종료로 유실될 수 있습니다. 이 계약은 이전의 매 프레임 패킷 보류 방식과 다릅니다.

## 저장 대상

| 대상 | 저장 내용 |
| --- | --- |
| 플레이어 | NBT, 인벤토리, 엔더 상자, 통계, 발전 과제 |
| 열린 메뉴 | 커서, 지원하는 바닐라 제작·거래 등의 임시 입력. 파생 결과 슬롯은 중복 저장하지 않음 |
| 세션 | 소유권 lease, epoch, 이동 예약·영수증 |

플레이어 `.dat`, 통계·발전 과제 파일 쓰기를 SQL로 대체합니다. 월드 블록·엔티티·SavedData(스코어보드·지도 등)·`level.dat`은 바닐라 파일로 저장합니다. 로그, 서버 설정, 플러그인이 직접 쓰는 파일은 SQL로 변환하지 않습니다.

**플레이어 데이터와 월드 파일은 따로 저장됩니다.** 이전의 통합 체크포인트와 달리 강제 종료 후 상자 안 아이템과 인벤토리가 같은 시점이 아닐 수 있어 복제·유실 구간이 생길 수 있습니다.

이전 빌드가 DB·SlimeVault에 저장한 영구 월드와 SavedData는 첫 시작 때 한 번 바닐라 파일로 내보냅니다. DB 사본은 삭제하지 않습니다. 절차는 [설치 안내](setup.md#이전-빌드의-월드-자동-내보내기)를 참고하세요.

## 최신 상태와 순서

최신 상태만 저장하고 복구는 `link_state`에서 수행합니다. 과거 이벤트 재생은 새 변경에 대해 지원하지 않습니다. 기존 이벤트 조회 API는 읽기 전용 호환 용도로 남습니다.

- 상태별 예상 버전으로 경쟁 쓰기를 검사합니다.
- 작업 UUID와 내용 검증으로 동일 요청의 재시도를 식별합니다.
- DB 시각 기반 lease와 증가하는 epoch로 이전 소유자의 쓰기를 차단합니다.
- 한 체크포인트의 여러 상태를 원자적으로 커밋합니다.

독립된 백엔드의 모든 작업에 하나의 전역 시간 순서를 부여하지 않습니다. Redis 알림은 중복·순서 변경이 가능하므로 소비자는 SQL 상태 버전을 다시 확인해야 합니다.

## 입장과 이동

각 백엔드는 기본 월드를 입장 채널로 등록합니다. 첫 입장은 채널 예약과 일회용 입장권을 거치며 Velocity가 살아 있는 노드를 배정합니다. 정원은 노드당 150명이 기본이며 예약자와 입장자를 함께 계산합니다. 백엔드는 입장권 소비와 소유권 획득을 처리하고, 플레이어는 저장된 위치(없으면 월드 스폰)에 바닐라 방식으로 배치됩니다. 예약된 월드·좌표·방향은 서버 간 이동 도착에만 적용합니다.

모든 자리가 소진되면 입장을 거부합니다. 영속 대기열과 백엔드 프로세스 생성은 미구현입니다.

서버 간 `/tpa` 이동은 목적지 예약 → 원본 메뉴 닫기와 최종 체크포인트 → 플레이어 동결·이전 준비 → 후속 프레임 커밋 → `READY` → 프록시의 `CONNECTING` 선점 → 목적지 입장권 소비·새 epoch 획득 순서입니다. 같은 백엔드 이동은 로컬 텔레포트로 처리합니다.

미완료 이동은 lease 만료 후 재접속으로 회복할 수 있습니다. 기본 lease는 30초이므로 즉시 재접속·재시작이 거부될 수 있습니다.

## 장애와 경계

Redis 연결·전송 재시도는 `Link-Notifications`에서 수행해 초기화와 lease 갱신을 막지 않습니다. 미전달 outbox는 SQL에 남깁니다. SQL 커밋이나 소유권을 유지할 수 없으면 게임 진행을 중단합니다.

이전 DB 월드 저장 구현의 51명 검사에서 TPS 4.6을 관측했습니다. 바닐라 월드 저장으로 전환한 뒤의 부하는 다시 측정해야 합니다. 탑승 관계와 서버 간 지도 데이터 복원도 실패했습니다. 엔더 진주 소유자·등록은 단일 백엔드 재시작 검사에서 통과했으며 모든 이동 조합을 검증한 것은 아닙니다.

외부 HTTP, 플러그인의 별도 DB·파일, 임의 가상 인벤토리, 비동기 Bukkit/NMS 변경은 프레임의 원자성 범위 밖입니다. 기존 플레이어 파일 가져오기, 범용 스키마 버전 이전 도구, 백업/PITR 및 전체 네트워크 복구 절차도 미완료입니다. 플레이어 DB와 월드 파일을 백업·복원할 때는 가능한 같은 시점으로 맞추세요.

내구성은 PostgreSQL WAL 또는 MariaDB InnoDB·binlog와 스토리지·복제 설정의 장애 모델에 의존합니다. 월드 파일의 내구성은 서버 디스크와 별도 백업에 의존합니다. 로컬 커밋만으로 DB 호스트 전체 손실까지 보장하지는 않습니다.
