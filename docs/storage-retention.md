# DB 증가 원인과 이벤트 보관

[설치](setup.md) · [검증](validation.md)

## 확인한 원인

`NativeJournal.checkpoint()`는 네이티브 프레임 종료 시 월드 SRF, SavedData, 플레이어 NBT를 직렬화합니다. `FrameCommitter`는 이전 바이트와 같으면 기록하지 않지만 바뀐 상태는 `EventStore`가 전체 after-state로 `link_events`에 추가하고 `link_state`도 갱신합니다.

- 빈 월드도 `minecraft:world_clocks.total_ticks`, `minecraft:weather` 타이머, `minecraft:raids.tick`, `paper:level_overrides.game_time`이 틱마다 변합니다. 20 TPS에서 네 값만으로 월드 하나당 초당 약 80행이 발생할 수 있습니다. 로드된 편집 월드도 포함됩니다.
- 플레이어 위치·통계 등이 바뀌면 압축된 전체 플레이어 상태를 새 이벤트로 저장합니다.
- SQL 월드 저장은 압축 SRF를 최대 8MiB 조각으로 나눕니다. 블록 하나가 바뀌어도 변경된 압축 조각 전체가 새 이벤트가 됩니다. 현재 구현은 청크·필드 단위 차분 저장이 아닙니다.
- MariaDB의 `link_locks`는 트랜잭션 작업 UUID마다 새 잠금 행을 남깁니다. `link_operations`는 중복 실행 방지용 영수증을 유지합니다.
- Redis outbox와 스트림은 별도 저장입니다. 기존 전송 주기는 백엔드당 5초에 최대 64건이어서 알림 생성이 초당 12.8건보다 많으면 미전달 행이 누적될 수 있습니다. Redis 스트림에는 현재 길이 제한이 없습니다.

로컬 MariaDB + SlimeVault 테스트 DB에서 이벤트 82,770행, 이벤트 payload 10.665MiB, 이벤트 테이블·인덱스 할당량 약 43.31MiB를 확인했습니다. 현재 상태는 124행, payload 약 18.36KiB였습니다. 이는 운영 DB 수치가 아닙니다. 사용자가 보고한 3일 16GB는 하루 약 5.3GB이며, 운영 원인의 비중은 테이블별 크기로 구분해야 합니다. DB 데이터 디렉터리 증가에는 테이블 외에 binlog/WAL도 포함될 수 있습니다.

읽기 전용 진단: [MariaDB](../link-integration/storage-diagnostics-mariadb.sql), [PostgreSQL](../link-integration/storage-diagnostics-postgresql.sql). 16GB 이벤트 테이블 전체를 집계하는 쿼리 대신 테이블 통계와 특정 aggregate의 최신 10개 이벤트를 먼저 확인합니다.

## 자동 정리

```yaml
retention:
  enabled: true
  event-hours: 24
  interval-seconds: 60
  batch-operations: 500
  max-batches: 10
```

기존 `link.yml`에 `retention` 항목이 없으면 해당 블록을 덧붙입니다. 기존 설정·주석·비밀번호를 다시 쓰지 않습니다. 변경 후 재시작해야 합니다. `disabled` 모드나 Velocity 단독 프로세스에서는 정리 작업을 실행하지 않습니다.

- 백엔드 전용 작업 스레드가 60초마다 실행합니다. 기본값은 한 번에 최대 500개 트랜잭션씩 10회 처리합니다. 기존 적체량은 여러 주기에 걸쳐 줄어듭니다.
- DB 시각 기준 24시간이 지난 작업 중 최신 상태를 포함하지 않는 작업의 이벤트를 **트랜잭션 전체 단위**로 삭제합니다. 최신 상태 하나라도 참조하는 트랜잭션은 전체를 남깁니다. 따라서 24시간 이전 이벤트가 일부 남는 것은 정상입니다.
- `link_state`, 월드/플레이어 복구 데이터, 템플릿, 소유권, 이동 데이터, 작업 digest는 삭제하지 않습니다. 같은 작업 UUID 재전송도 중복 실행하지 않습니다.
- 티피 요청은 만료 시각이 보관 기간보다 오래된 `link_teleport_requests` 행도 정리합니다. 요청자별 최신 `tpa:` 상태와 멱등성 기록은 남습니다.
- 전송 완료된 오래된 outbox만 삭제합니다. 미전달 outbox는 보존합니다. Redis를 끄면 미전달 행은 계속 남으므로 이 정책만으로 모든 테이블의 증가가 없어지는 것은 아닙니다.
- 여러 백엔드가 같은 DB를 사용해도 SQL 행 잠금과 `SKIP LOCKED`로 중복 정리를 피합니다. 정리 오류 시 해당 SQL 트랜잭션을 롤백하며 다음 주기에 재시도합니다. 정리 실패 때문에 게임 서버를 종료하지 않습니다.
- 삭제된 과거 이력의 재생은 지원하지 않습니다. `history` 결과에는 보관 정책에 따른 버전 간격이 생길 수 있습니다. 플러그인은 전체 과거 이력이 필요하면 별도 보관하고, 현재 상태 동기화에는 `data().read()`를 사용해야 합니다.

첫 실행 시 정리용 컬럼·인덱스가 추가됩니다. 큰 기존 이벤트 테이블에서는 인덱스 생성에 시간이 걸리고 추가 디스크 공간이 필요할 수 있습니다. 별도 서버 DB에 이번 작업으로 직접 접속하거나 데이터를 삭제하지 않았습니다.

## 이 정리가 해결하지 않는 것

이벤트 삭제는 현재 상태 복구를 보존하면서 온라인 이력의 증가를 줄입니다. **쓰기 발생량 자체를 줄이는 변경은 아닙니다.** 또한 삭제 후 DB 파일이 즉시 작아지는 것은 아닙니다. 엔진이 페이지를 재사용할 수 있게 되는 것과 운영체제에서 확인하는 파일 크기는 구분해야 합니다. 기존 16GB 파일의 회수는 실제 DB 종류·빈 공간·복제 구성에 맞춰 별도로 진행합니다.

SlimeVault 객체는 이 작업에서 삭제하지 않습니다. 이벤트가 가리키던 객체라도 현재 상태·템플릿·백업에서 필요할 수 있어 참조 검증 없는 삭제는 금지합니다. S3 저장은 SQL 월드 본문을 외부로 옮기는 기능이며 모든 누적 문제의 해결책은 아닙니다.

쓰기량을 추가로 줄이는 후속 개선은 청크/필드 단위 변경 기록과 주기적인 전체 스냅샷, 비어 있는 작업 월드 언로드, 알림 전송 처리량 개선 및 스트림 보관 정책, MariaDB 잠금 행 수명 관리입니다. 인벤토리 저장 간격만 늘리는 방식은 패킷 공개 전 커밋과 장애 시 복구 계약을 바꾸므로 적용하지 않습니다.
