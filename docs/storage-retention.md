# 최신 상태 저장과 기존 이벤트 정리

[설치](setup.md) · [검증](validation.md)

## 저장 방식

새 커밋은 `link_events`에 기록하지 않습니다. `link_state`의 최신 상태, `link_operations`의 작업 UUID·digest, `link_outbox` 알림을 한 SQL 트랜잭션에 저장합니다. 예상 버전 검사, 세션 소유권·epoch 검사, 커밋 응답 유실 시 동일 작업 재시도는 유지됩니다. 게임 패킷은 저장 완료를 기다리지 않습니다. PostgreSQL WAL이나 MariaDB InnoDB 로그를 끄는 변경이 아닙니다.

`EventStore`, `NativeJournal`, `journal` 모드 이름은 호환성을 위해 유지합니다. 이름과 달리 새 변경의 이벤트 소싱·과거 리비전 재생은 하지 않습니다. `data().history()`는 deprecated 읽기 전용 API이며 남아 있는 구버전 이벤트만 반환합니다.

## 월드 저장

월드 메타데이터와 청크별 SRF를 분리합니다. 청크 내용의 SHA-256을 비교하여 변경된 청크만 압축하고 SQL 또는 SlimeVault S3에 저장합니다. 인덱스·청크·플레이어·SavedData는 같은 체크포인트에 원자적으로 커밋합니다. 삭제된 청크와 교체된 큰 바이너리의 남은 조각은 빈 payload로 덮어씁니다.

자동 저장 기본 주기는 30초입니다. 매 틱·매 작업마다 캡처하지 않습니다. 저장 시 서버 스레드에서 청크·플레이어·SavedData의 분리된 복사본을 만들고, 기본 4개 작업 스레드가 청크 직렬화·해시·압축·S3 업로드를 병렬 처리합니다. SQL 커밋은 전용 저장 스레드 하나가 순서대로 수행합니다.

동시에 처리하는 체크포인트는 하나입니다. 이전 저장이 진행 중이면 다음 자동 저장을 중복 큐에 쌓지 않습니다. 저장 완료 콜백은 서버 스레드에서 처리합니다. `/save-all`과 `/save-all flush`도 비동기 저장 완료 후 성공 메시지를 보내며, 서버 이동과 정상 종료는 최종 저장 완료를 기다립니다.

**메모리에서 진행된 게임은 마지막 저장 이후 강제 종료되면 유실될 수 있습니다.** 월드는 재시작마다 템플릿으로 초기화되지 않으며 마지막 완료된 월드 변경을 복구합니다. 플레이어와 설정의 DB 저장도 유지됩니다.

```yaml
saving:
  interval-seconds: 30
  workers: 4
```

기존 YAML에도 블록을 추가합니다. 주기는 1~3600초, 작업 스레드는 1~16개이며 재시작 후 적용됩니다.

저장 시 전체 청크의 내용 캡처와 비교는 여전히 수행합니다. 블록 변경 플래그 하나로는 엔티티 이동, 블록 인벤토리, PDC, 조명, POI, 예약 틱을 충분히 추적할 수 없기 때문입니다. 따라서 스키매틱 붙여넣기의 NMS·조명 계산·메인 스레드 캡처 비용까지 없어지지는 않습니다. 실제 WorldEdit/FAWE 작업의 속도 향상을 보장하는 수치는 아닙니다.

청크 체크포인트는 빈 청크도 보존하여 PDC만 있는 청크를 제거하지 않습니다. 템플릿 발행·명시적 전체 SRF 내보내기는 기존 ASP 기능을 사용합니다. 한 트랜잭션의 상한은 65,536개 상태 조각입니다. 대형 월드 최초 전환은 모든 청크를 기록하므로 평상시보다 오래 걸릴 수 있습니다.

## 기존 DB 전환

1. 모든 백엔드와 Velocity를 종료하고 SQL 및 참조하는 S3 객체를 함께 백업합니다.
2. 백엔드 JAR와 Velocity 플러그인을 모두 이번 버전으로 교체합니다. 구버전과 혼용하지 않습니다.
3. 시작 시 기존 `link_state`에서 복구합니다. 구형 전체 SRF 월드는 첫 체크포인트에서 청크 형식으로 원자적으로 전환됩니다. 기존 대형 SRF 상태 조각은 빈 payload가 됩니다.
4. 새 청크 인덱스가 존재하는데 필수 조각이 없거나 체크섬이 틀리면 복구를 중단합니다. 오래된 전체 SRF로 조용히 대체하지 않습니다.

구버전 바이너리는 새 청크 형식을 읽지 못합니다. 되돌릴 때는 전환 전 백업을 함께 복구해야 합니다. 운영 DB에는 이 개발 작업으로 접속하거나 데이터를 삭제하지 않았습니다.

## 자동 정리

```yaml
retention:
  enabled: true
  event-hours: 24
  interval-seconds: 60
  batch-operations: 500
  max-batches: 10
```

기존 `link.yml`에 항목이 없으면 기본 블록을 추가합니다. 백엔드 작업 스레드가 구형 이벤트를 최대 500개 작업씩 10회 정리합니다. 이제 최신 리비전의 구형 이벤트도 만료됩니다. 복구 원본인 `link_state`와 중복 요청 영수증은 삭제하지 않습니다. 새 작업은 처음부터 `events_pruned=true`로 생성하여 이벤트 정리를 위한 추가 UPDATE를 하지 않습니다.

전송 완료된 오래된 outbox와 만료된 티피·채널 대기 요청도 정리합니다. 미전달 outbox, 최신 상태, 템플릿, 소유권·이동 데이터는 보존합니다. 여러 백엔드는 행 잠금과 `SKIP LOCKED`로 함께 정리할 수 있고 실패한 정리 트랜잭션은 롤백됩니다.

## 용량에 남는 영향

기존 운영 통계는 `link_events` 15GB, `link_operations` 589MB, `link_outbox` 417MB, `link_state` 약 3.6MB였습니다. 새 이벤트 payload 증가는 중단되지만 다음 항목은 별개입니다.

- 과거 이벤트 삭제 후 SQL 파일이 즉시 줄어들지는 않습니다. 빈 페이지 재사용과 운영체제에 공간 반환은 다릅니다. PostgreSQL의 파일 회수 작업은 별도 점검 후 진행합니다.
- 작업 영수증은 중복 실행 방지를 위해 보존합니다. MariaDB 잠금 행, WAL/binlog, 최신 상태 UPDATE에 따른 공간·쓰기 비용은 남습니다.
- 미전달 outbox와 Redis 스트림은 별도 관리 대상입니다. Redis가 꺼져 있으면 미전달 알림이 누적됩니다.
- S3의 이전 리비전은 자동 삭제하지 않습니다. 현재 상태·템플릿·백업의 참조를 확인하는 별도 객체 보관 정책이 필요합니다.

읽기 전용 진단: [MariaDB](../link-integration/storage-diagnostics-mariadb.sql), [PostgreSQL](../link-integration/storage-diagnostics-postgresql.sql).
